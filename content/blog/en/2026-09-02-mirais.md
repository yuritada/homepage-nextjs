# Rebuilding My Department's Annual Research Showcase on a ¥3,000 Budget

**MIRAIS — Integrated Portal for the Mirai Sozo Research Showcase: design notes (summary)**

With a team of three, I designed and built a portal system that unifies the annual research showcase of the Faculty of Data Science at Musashino University — from preparation all the way through to the awards ceremony. I led the project, owning the overall design and the backend.

This post is the **short version** of the design and implementation record. The full text is published separately as a six-part series (links at the end).

Rather than listing technologies, I have written about **how decisions were made under constraints**. I think that is more useful to a reader than the details of the implementation.

---

## The three-line version

- The showcase was run on **manual re-typing from form → spreadsheet → website**, plus individual messages over chat.
- We unified it into one portal: **authentication, submissions, matching, a 3D exhibition, voting, awards, and print-material generation**.
- The development budget was **¥3,000** (about US$20). That constraint is what produced an architecture resilient to external failures.

| Item | Value |
| --- | --- |
| Backend | ~6,700 lines / 17 routers / 13 services (Python + FastAPI) |
| Frontend | ~5,300 lines / 20 pages (TypeScript + Next.js App Router) |
| 3D venue | ~3,100 lines / 12 files (React Three Fiber) |
| Data model | 20 tables (PostgreSQL 16) |
| Roles | 4 + logged-out + development |
| Development budget | ¥3,000 |

---

## Where it started: the same manual work, every year

The showcase was run roughly like this:

```
1. Send invitations to companies and tally who is attending
2. Create a form for students and collect their research topics
3. Compile the topics into a spreadsheet, then re-type them onto the website
4. Assign who presents in which of the three sessions
5. Send poster-printing and arrival-time instructions individually
```

Students had their own version: fill in a form, make a poster, save it somewhere hard to find, print it yourself, and keep it safe until the day. And how the visiting companies experienced any of this was **invisible to the organisers**.

We compressed the goal into a single sentence:

> **Everyone involved in the showcase completes the whole journey — from preparation to the awards — inside this portal, and the friction people have felt until now ends with our cohort.**

We also set a precondition: this must not end as a hackathon submission. It had to be designed as **infrastructure that keeps running in the years that follow**. If it stops working once its authors graduate, nothing has actually been solved.

---

## The constraint decided the design

The development budget was ¥3,000. That single number directly determined the following:

- Do not depend on a commercial LLM API. Make the **LLM running on the university's own GPU server** the first choice, and make sure nothing stops working in an environment where it is unavailable.
- Do not use an external SaaS for authentication. Verify Google ID Tokens and issue our own JWTs.
- Host on the university's own computing resources.

The result is this shape:

```
External integrations (all optional; the system runs without any of them)
  ├─ University LLM server   … embedding generation
  ├─ Slides API             … award / booth-guide slides
  ├─ Spreadsheet API        … export of submissions, companies, awards
  ├─ Storage API            … archiving student posters
  ├─ Google Identity        … campus OAuth
  └─ Chat tool              … reminders for missing submissions
```

If the university LLM is down, recommendations still work. If the slides API is unconfigured, the portal still works. Without the chat integration, reminders are still recorded in the history.

Without the constraint, we would have simply called a commercial API — and **everything would have stopped on the day it went down**. Thinking in the order "there is no budget, therefore this is the architecture" rather than "there is no budget, so we give up" is what made the architecture coherent.

## One sentence in an interview decided the data model

I sat down with the administrative staff member who runs the showcase and walked through their work along the annual calendar. It is the highest-density primary information in the whole project.

One remark — **"it doesn't have to end up in the same shape as the spreadsheet we manage today"** — is what made it possible to treat our own database as the single source of truth. Without it, we would have been dragged into the existing spreadsheet's shape and ended up with a far more cramped data model.

Other requests that came up almost in passing became features verbatim:

| What I was told | The feature it became |
| --- | --- |
| "I want to be able to change the background image every year" | A no-code settings screen for organisers (design elements held as data) |
| "Producing the sheet *before* it gets cut up could probably be automated" | A4 imposition data for name tags |
| "The slip we stick above the poster, saying who presents there and when" | Auto-generated booth-guide slides (one slide = one booth position) |
| "It would be good to prepare a template, copy it, and fill in the data" | Auto-generated award slides (duplicate the template, replace placeholders) |
| "We collect by two weeks before. We plan **assuming people will be late**" | Automatic reminders, promoted from "nice to have" to essential |

### Deciding what *not* to automate

The bigger lesson was the opposite kind of decision.

Collecting company logos involves the partner's internal approval process and takes time, so the organisers place them by hand. Automating that would have meant **dragging the partner's approval process into the system**. But if you accept "the organiser pastes it in by hand" as the workflow, all you need is one column storing an image URL and a field to paste it into.

We limited spreadsheet sync to a **one-way export** rather than two-way. Bidirectional sync means conflict resolution, which means the risk of corrupting data. Restricting it to one direction meant the sync logic was simple and unbreakable, someone hand-editing the spreadsheet could never contaminate the database, and the spreadsheet went on serving as "a backup, and the view the organisers are used to".

**Rather than forcing a workflow through the system, accept the existing one and build the feature that makes it take the fewest steps.** "User first" does not mean granting every request. Deciding where *not* to touch someone's workflow is just as much a part of design.

## Hiding a field and withholding data are different problems

This is the rule we enforced most strictly.

A poster PDF may contain the student's name and ID number, their supervisor's name, the lab name, and the names of collaborating companies. In a research poster, all of that is normally printed on the sheet.

So for logged-out visitors we set this policy:

```
- Return only the "title" and "abstract" of a piece of research.
- Names, tags, seminar names, poster URLs, comments, votes and so on are
  excluded from the API entirely (so the requirement to strip them from the
  DOM outright is genuinely satisfied).
- No additional fields may be added here.
  If a field is needed, serve it from an authenticated route.
```

Someone suggested simply branching on the frontend, but then anyone inspecting the traffic can read the data. Hiding it in CSS is of course out of the question. **Not putting it in the API response** was the only reliable guarantee, so the public response model is defined as a type with exactly three fields.

The reason for making it a type: if someone who does not know this policy later tries to add a field, they must **explicitly change the type** to do so. The structure should not leak by accident.

We also accepted the cost. Because poster PDFs now require authentication, they cannot be displayed through the `src` of an `<img>` or `<iframe>` (neither can send custom headers). Instead we fetch the PDF with the auth header, build a blob URL from it, and feed that into the iframe. The lesson: **a decision comes bundled with its implementation cost**.

## Translating a workflow directly into an algorithm

Interviews revealed how awards actually worked:

- Participating companies have a **ranking**, maintained by hand.
- The seminars supply a **shortlist for the departmental award**, and companies **promote** entries from it to their own company award.

We translated that into a two-phase algorithm.

**Phase 1 (faculty nominations)**: 30 nomination slots are distributed across seminars in proportion to student numbers. Simple rounding does not sum to 30; truncation leaves slots unused. So we used the **Hamilton method** (largest remainder) — hand out leftover slots one at a time, in descending order of fractional part — which keeps the total exact while preserving proportionality as far as possible. Tie-breaking has three stages, to guarantee that **the result never changes between runs**. "The quotas were different yesterday" is the kind of bug that loses the organisers' trust.

**Phase 2 (company selection)**: walk approved companies in descending order of ranking, follow each company's ranked votes, claim the first submission that is "in the nomination pool and not yet claimed by another company", and promote that record from departmental award to company award.

Four rules are embodied in this design:

- A company award is **always drawn from the departmental nomination pool**. No student wins purely on a company's say-so without a faculty nomination.
- **Higher-ranked companies choose first.**
- **One award per student.**
- **Idempotent** — running it repeatedly gives the same result.

That last property was missing in the first implementation. We had not written the step that returns previously selected company awards to the nomination pool, and it surfaced as a bug: "the pool of candidates shrinks every time you run it." **Idempotency is not something you bolt on afterwards; it belongs in the design from the start.**

One more thing. The combined run only executes Phase 1 when the nomination pool is empty, and never overwrites an existing one — so that a pool a professor has adjusted by hand cannot be wiped out because an organiser happened to press the automation button. **Automation goes only as far as it does not overwrite a human judgement.** Same instinct as accepting the copy-and-paste workflow for logos.

## Recommendations keep working when the LLM is down

Companies write a free-text description of their interests; research abstracts are vectorised; recommendations come from cosine similarity. Because of the budget we use the university's LLM server — but we also assumed it might not be usable.

```
University LLM server not configured → use the mock embedding
Configured                           → call the API, normalise on success
Call failed                          → fall back to the mock embedding
```

The fallback path is built seriously too. Japanese tokens are expanded into 2-grams (`"機械学習"` / *machine learning* → `["機械学習", "機械", "械学", "学習"]`), then accumulated into buckets via a 256-dimension hashing trick and L2-normalised. This captures partial matches in Japanese without adding a morphological analyser as a dependency, handles unknown words because there is no vocabulary table, and uses a fixed amount of memory.

And it is **deterministic**. The same input always produces the same vector, which guarantees reproducibility in a live demo.

That was an implementation of the requirement and an insurance policy at the same time. Designing away the chance that an external dependency dies during a five-minute demo — not having to stand in front of people carrying the worry that "this might not work" — turned out to matter more than I expected.

## Not letting the 3D venue be a tech demo

A new correspondence-course faculty opened this year. How do you give students who are far away a place to exhibit? The 3D virtual venue is positioned as a direct answer to that question.

It is true that the wish to "try using 3D" came first. Refusing to let it end as a showcase of technology, and redesigning it as an answer to a concrete problem in front of us, is one of the things I cared about most in this project.

We extracted coordinates from the venue's actual floor plan and mapped them into 3D space. We deliberately told one lie here: the building's footprint is **scaled to twice its real size, while heights stay at 1:1**. At true scale it felt cramped to walk around as an avatar. The relative positions of the booths remain accurate, though, so the real purpose — "which research is in which area" — is unharmed. **Deciding what to keep accurate and what to sacrifice is what design is.**

The final piece was synchronising with the physical venue:

> When an organiser sets "we are now in session 2", **all 36 poster surfaces in the venue switch to session 2's presenters within three seconds**.

The changeover on site and the changeover in the 3D space happen together. Only once that worked did the 3D venue become a genuine substitute for exhibiting.

The fiddliest part, incidentally, was real data. Booth numbers imported from CSV come in as `"1-27"`, `"27"`, `"01-05"`, `" 27 "`; sessions arrive as `"1"`, `"part_1"`, and `1`. We started from the premise that **real data is not clean** and absorbed the variation on the reading side — rewriting historical data would have destroyed the record of what was actually there at the time.

## What is honestly still missing

This is the public version, so I will not name specific locations — only the nature of each item. These three are the top priority:

- **Inconsistent authorisation granularity.** We defined a strict public-data policy, but some features added later did not apply it rigorously. Guarding a policy with prose and comments is not enough; it needed to be **enforced mechanically, through types and shared dependencies**.
- **No schema-migration mechanism.** This follows from choosing "create the tables automatically at startup" early on. Comfortable during development, but once the system is in operation there is no way to add a column. This is debt that must be cleared before the operational phase.
- **No automated tests.** Frankly the biggest problem. Logic like the award algorithm — many branches, high cost when wrong — is currently guaranteed only by manual checking. This should be filled in before any new features are added.

Beyond those: no rate limiting, no audit log, no continuous dependency-vulnerability scanning, and no structured logging or monitoring. Automatic execution of reminders is also the one feature still only partially implemented — introducing a bot into the campus chat tool requires an application process, so the bottleneck there is organisational rather than technical.

## Three things I learned

**1. Constraints make a design clear**

The ¥3,000 budget looked like an obstacle at first. In practice it forced a chain of decisions — "we cannot depend on a commercial API" → "use the university's own resources" → "make it work even when those are unavailable" — and produced an architecture resilient to external failure.

**2. Decide where not to touch someone's workflow**

Choosing not to automate logo collection, limiting sync to one direction, matching the existing "copy the template and fill it in" work model — all of them are decisions to *not* do something we could have done. What a system should solve is the user's problem, not the user's job. **Deciding what not to build is part of design.**

**3. Requirements are never complete at the start, so fix the axis first**

Early in the planning, the team agreed on this:

> The detailed requirements will change a great deal. But **we want to hold the core experience — the essential part — unchanged all the way through.**

And the requirements did change enormously. The table count went from 7 to 20, and 11 features that were not in the design were added. We never got lost anyway, because we had drawn the line between what was allowed to change and what was not, right at the start. **A plan robust to change is not a detailed plan; it is a plan with a clear axis.**

Honestly, this project started as little more than "I want to build a website for the showcase". That it ended up as a system with a 20-table data model and three applications is entirely because people gave me their time and told me how the work actually goes.
